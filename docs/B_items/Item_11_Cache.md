اصول پایه — سه راهکار کاهش فشار API

راهکار اول — Coalescing (ادغام درخواست‌ها)

مسئله: اگر ۱۰۰ کاربر همزمان داده BTC یک ماهه بخواهند، بدون Coalescing یعنی ۱۰۰ درخواست جداگانه به صرافی. این کار IP را بلاک می‌کند.

راه‌حل: Coalescing در دو سطح انجام می‌شود. سطح اول، سطح Scanner است. اگر ۱۰۰ کاربر درخواست یکسان بدهند (همان دارایی، همان بازه، همان تایم‌فریم)، سیستم فقط یک Scanner Job می‌سازد و نتیجه را به همه ۱۰۰ کاربر می‌دهد. سطح دوم، سطح Fetch است. اگر ۱۰۰ درخواست مختلف، به داده خام یکسانی نیاز داشته باشند (مثلاً همه به BTC/USDT یک ماهه از Binance نیاز دارند)، سیستم فقط یک Fetch می‌زند و از همان داده برای همه استفاده می‌کند.

تأثیر بر Rate Limit: بدون Coalescing، فشار API با تعداد کاربران رشد خطی دارد. با Coalescing، فشار API تقریباً ثابت می‌ماند، چون درخواست‌های یکسان ادغام می‌شوند.

ارجاع: جزئیات Coalescing Keys و Scanner-level و Fetch-level در بخش‌های بعدی همین Item_11 طراحی می‌شود. Item_09 فقط محدودیت عددی را ثبت کرده است.

---

راهکار دوم — Gap-Aware Fetch (فچ فقط بخش گمشده)

مسئله: Collector هر چهار ساعت کش را آپدیت می‌کند. اگر کاربر ساعت ۱۵:۳۰ درخواست بدهد و Collector ساعت ۱۲:۰۰ آپدیت کرده باشد، فچ کردن کل چهار ساعت اتلاف است. فقط باید از ۱۲:۰۰ تا ۱۵:۳۰ فچ شود.

راه‌حل: سیستم گپ را محاسبه می‌کند (فاصله بین آخرین آپدیت Collector و end timestamp کاربر). فقط همان گپ فچ می‌شود. اگر گپ صفر باشد (یعنی end timestamp کاربر قبل از آخرین آپدیت Collector باشد)، صفر فچ انجام می‌شود.

تأثیر بر Rate Limit: Gap-Aware Fetch تعداد درخواست‌ها را به طور قابل توجهی کاهش می‌دهد. به جای فچ کردن کل بازه، فقط بخش گمشده فچ می‌شود. برای درخواست‌های تاریخی (مثلاً end قبل از آخرین آپدیت)، فشار API صفر است.

ارجاع: Item_09 فقط تعریف گپ را ثبت کرده. تبدیل گپ به بازه کندل و نحوه فچ در همین Item_11 طراحی می‌شود.

---

راهکار سوم — Cache Window و Eager/Lazy Fill

مسئله: Cache Window (پنجره پنج دقیقه‌ای) تعیین می‌کند که داده چقدر تازه است. اگر کش قدیمی باشد، STALE علامت می‌خورد و کاربر باید منتظر فچ جدید باشد. طراحی درست Cache Window مستقیماً بر تعداد فچ‌های API اثر می‌گذارد.

راه‌حل: دو استراتژی وجود دارد. Eager Fill یعنی وقتی کاربر درخواست می‌دهد، سیستم فوراً گپ را فچ می‌کند (حتی اگر هنوز کاربر دیگری نیاز نداشته باشد). Lazy Fill یعنی سیستم صبر می‌کند تا کاربر بعدی درخواست بدهد و آن‌وقت فچ می‌کند. Eager Fill تجربه کاربر را بهتر می‌کند ولی فشار API را بیشتر می‌کند. Lazy Fill فشار API را کمتر می‌کند ولی ممکن است کاربر اول منتظر بماند.

تأثیر بر Rate Limit: انتخاب بین Eager و Lazy مستقیماً تعداد فچ‌ها را تعیین می‌کند. برای Default Range که همیشه end=الان دارد، Eager Fill منطقی است. برای Custom Range تاریخی، Lazy Fill منطقی‌تر است.

ارجاع: تصمیم نهایی بین Eager و Lazy در همین Item_11 گرفته می‌شود. Item_09 فقط پنجره پنج دقیقه‌ای را به عنوان Cache Window ثبت کرده است.

---

خلاصه تأثیر سه راهکار بر فشار API

بدون هیچ راهکاری: فشار API با تعداد کاربران رشد خطی دارد. ۱۰۰ کاربر = ۱۰۰ برابر فشار. IP بلاک می‌شود.

با Coalescing: فشار API تقریباً ثابت می‌ماند. ۱۰۰ کاربر با درخواست یکسان = ۱ فچ. فقط ۱۰۰ کاربر با ۱۰۰ درخواست مختلف = ۱۰۰ فچ.

با Coalescing و Gap-Aware Fetch: فشار API حتی برای درخواست‌های مختلف هم کاهش می‌یابد. چون فقط گپ فچ می‌شود، نه کل بازه.

با Coalescing و Gap-Aware Fetch و Lazy Fill: فشار API به حداقل می‌رسد. فقط وقتی کاربر واقعاً نیاز دارد، فچ انجام می‌شود.

سوالات باز برای Item_11 (نه Item_09)

سوال اول: آیا Coalescing در سطح Scanner باید کلید دقیق داشته باشد یا می‌تواند تقریبی باشد؟ (مثلاً دو درخواست «یک ماهه» با اختلاف چند ثانیه در end timestamp — آیا یکی هستند؟)

سوال دوم: برای Gap-Aware Fetch، تبدیل گپ به بازه کندل چطور انجام می‌شود؟ (مثلاً گپ ۳.۵ ساعت = چند کندل ۵ دقیقه‌ای؟)

سوال سوم: Eager Fill و Lazy Fill — کدام برای کدام نوع درخواست؟ (پیشنهاد اولیه: Default = Eager، Custom تاریخی = Lazy)

سوال چهارم: in_use_by_jobs counter — چه زمانی صفر می‌شود؟ (وقتی همه Jobهای فعال تمام شوند، یا با timeout؟)
