بخش ۰ — هدف و دامنه

این پارت، صف ارسال (Outbox)، مدیریت وضعیت تحویل و هماهنگی ارسال Payload نهایی از طریق Package D را طراحی می‌کند. هدف ما تضمین «ثبت پایدار و تلاش برای تحویل» است.

تصمیم Owner (O-1): تحویل دقیقاً یک‌بار (Exactly-Once) در تلگرام قابل تضمین نیست. بنابراین در صورت Timeout، سیستم Retry می‌کند و احتمال ارسال تکراری به جای گم شدن پیام، پذیرفته می‌شود.

تعاملات کاربر با منوها و دکمه‌ها (Callbacks) در Package D مدیریت می‌شوند و از صف Outbox عبور نمی‌کنند.

بخش ۱ — چرخه حیات پیام در Outbox

Item_11 مالک State Machine منطقی است و Item_12 مسئول Persistence و Atomic Claim فیزیکی است.

۱.۱ وضعیت‌های پیام اصلی (Parent)

PENDING: پیام ثبت شده و منتظر ارسال است.

SENDING: حداقل یک قطعه از پیام در چرخه ارسال قرار دارد.

DELIVERED: تمام قطعات پیام با موفقیت توسط Telegram پذیرفته شده‌اند.

PARTIAL: بخشی از قطعات ارسال شده‌اند، اما تحویل کامل نشده است.

RETRY_WAIT: پیام منتظر تلاش مجدد طبق Item_10 است.

FAILED: پیام به دلیل خطای غیرقابل جبران از چرخه ارسال خارج شده است.

۱.۲ وضعیت‌های هر قطعه (Chunk)

هر قطعه وضعیت مستقل دارد:

PENDING | SENDING | DELIVERED | RETRY_WAIT | DELIVERY_UNKNOWN | FAILED

۱.۳ مشتق‌سازی وضعیت پیام اصلی از قطعات (Parent State Precedence)

وضعیت گزارش اصلی از وضعیت قطعات آن با ترتیب تقدم زیر (از بالا به پایین) مشتق می‌شود:

۱. اگر حداقل یک قطعه به FAILED نهایی رسیده باشد و تکمیل Parent دیگر ممکن نباشد → Parent = FAILED

۲. اگر تمام قطعات DELIVERED باشند → Parent = DELIVERED

۳. اگر حداقل یک قطعه در حال ارسال (SENDING) باشد → Parent = SENDING

۴. اگر حداقل یک قطعه در RETRY_WAIT یا DELIVERY_UNKNOWN باشد → Parent = RETRY_WAIT

۵. اگر حداقل یک قطعه DELIVERED شده باشد و سایر قطعات هنوز تکمیل نشده باشند → Parent = PARTIAL

۶. اگر هیچ قطعه‌ای DELIVERED نشده و ارسال هنوز شروع نشده باشد → Parent = PENDING

قاعده: قطعات DELIVERED در تمام حالت‌ها از چرخه ارسال مجدد خارج هستند.

بخش ۲ — کنترل نرخ (Pacing) و اولویت‌بندی

۲.۱ Pacing Reservation (عملیات اتمیک)

Global Pacing: سقف اجرایی ۲۵ پیام در ثانیه برای کل ربات (ثبت‌شده در Item_09).

Per-User Pacing: حداقل فاصله یک ثانیه بین دو پیام تحلیلی به یک کاربر (تصمیم Owner O-2).

عملیات اتمیک: بررسی و رزرو مجوز (Token) باید یک عملیات غیرقابل تفکیک (Atomic) میان تمام Dispatcherها باشد.

انقضا و آزادسازی: رزرو Pacing باید موقت باشد. اگر Atomic Claim ناموفق شود، مجوز رزروشده باید آزاد شود یا پس از مدت اعتبار کوتاه منقضی شود. مجوز فقط پس از Claim موفق برای ارسال همان قطعه قابل استفاده است.

هر مجوز فقط برای یک قطعه صادر می‌شود. اگر مجوز موجود نباشد، قطعه در صف می‌ماند.

۲.۲ Priority

Package D هنگام تحویل Payload، اولویت (HIGH یا LOW) را در Metadata مشخص می‌کند. Item_11 صرفاً زمان‌بندی را اجرا می‌کند.

سیاست ضد گرسنگی: پس از هر پنج پیام HIGH، در صورت وجود پیام LOW، یک پیام LOW انتخاب شود.

این سیاست مستقل از Background Fetch Queue است.

وضعیت شمارش ارسال‌های موفق HIGH باید به‌گونه‌ای قابل بازیابی باشد که با Restart شدن Dispatcher، ترتیب اجرای این سیاست از بین نرود. این کار باید با استفاده از اطلاعات موجود در Outbox انجام شود و به جدول جدید نیاز ندارد.

نکته حیاتی (مرز Chunking و Markdown):

Package D باید Payload قالب‌بندی‌شده را به‌گونه‌ای تحویل دهد که نقاط امن تقسیم برای Chunking فنی مشخص یا قابل تشخیص باشند. Item_11 مجاز به تغییر معنای محتوا، حذف ساختار Markdown یا بازنویسی گزارش نیست. اگر تقسیم ایمن ممکن نباشد، Payload باید برای مدیریت به Package D بازگردانده شود.

بخش ۴ — حالت‌های خاص

۴.۱ Delivery Uncertainty (Timeout)

Timeout با نتیجه نامشخص، قطعه را وارد وضعیت DELIVERY_UNKNOWN می‌کند.

تصمیم قطعی Owner (O-1): این وضعیت باید وارد چرخه Retry شود و احتمال ارسال تکراری پذیرفته شده است.

پس از تعیین زمان تلاش مجدد توسط Item_10، وضعیت قطعه به RETRY_WAIT تغییر می‌کند.

Item_10 نوع خطا و زمان تلاش مجدد (Backoff) را تعیین می‌کند.

قطعات DELIVERED از چرخه Retry خارج هستند.

۴.۲ Telegram Rate Limit (429)

پس از دریافت 429:

Item_10 محدوده اثر محدودیت (مثلاً یک کاربر خاص یا کل ربات) و زمان مجاز برای تلاش مجدد را تعیین می‌کند.

Item_11 ارسال‌های مشمول محدودیت را تا پایان Backoff متوقف می‌کند.

ارسال‌های خارج از محدوده محدودیت، در صورت داشتن مجوز Pacing، می‌توانند ادامه پیدا کنند.
